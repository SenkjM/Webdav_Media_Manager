# 10 · 顺手做清单

> 编号 10 · 总索引：[00-INDEX.md](00-INDEX.md)

放大工程里那些**独立、顺手、不值得单开一轮**的小任务。写的是边界与判断条件，不是待办催办单：**发不发布、拆不拆、何时做，都由用户决定。**

## 用法（agent 必读）

1. **不主动执行**。只有用户在清单里挑了某项、或本轮工作天然覆盖到它，才动手。
2. 判断「适合顺手做」必须**四条同时满足**：边界能与其它改动切开；一屏以内的小改或纯机械批量改；不需要新的设计决定；不阻塞当前主线。任一条不满足就留在清单里。
3. **合并前先问用户**，并说清合并理由（共享同一段代码 / 顺路一起验证 / 同一次编译与测试成本 / 改动量很小）。只列理由，不替用户决定。
4. 完成一项就**从清单删掉**，语义按完整文档的写法写进对应功能块，并删掉 99 里的对应条目。
5. 新发现的小任务写进这里，标注它从哪次工作冒出来（来源）、边界条件、判断条件；还没定型的分析仍写在 [99-IN-PROGRESS.md](99-IN-PROGRESS.md)。

## 清单

### T1 · 主题配色：静态引用转上下文取色  `待发布`

- **来源**：主题配色可行性分析（[99 §4](99-IN-PROGRESS.md)）。
- **目标**：`AppColors` 的 325 处静态引用（24 个文件）改成上下文取色，让 `AppTheme.dark` 从死代码变成可用；默认仍是 `ThemeMode.light`，**亮色下行为不变**。
- **适合顺手的时机**：本轮改动正好涉及显示层，或用户在整理界面样式。
- **判断条件**：机械批量改、不引入新设计、完成后亮色表现完全一致（可对照截图验收）。
- **边界**：`nearBlack` / `onDark` 这类语义在暗色下会**反转**，必须单独判断，不能机械替换。
- **验收**：`flutter analyze` + `flutter test`；亮色截图与改动前一致。

### T2 · 主题配色：模式开关与自定义取色  `待发布`

- **来源**：同上；**依赖 T1 完成**。
- **目标**：三态开关（跟随系统 / 亮 / 暗）持久化到 `SettingsService`；自定义配色。
- **先问用户**：自定义的边界是「只让用户改主色 accent」还是「整套色板」。前者工作量小得多，但 `onAccent` 的对比色要跟着算出来。这条**未定就不能开工**。
- **判断条件**：T1 已落地，且用户已经确认了自定义边界。

### T3 · `_SelectableGroupGrid` 的返回键兜底  `待发布`

- **来源**：音乐库子界面返回键那几轮修复（见 [99 §2](99-IN-PROGRESS.md) 与 [03](03-MUSIC-LIBRARY.md)）。
- **目标**：专辑 / 流派网格的子界面（`_TrackListPage` 之外的那条路径）也补上同样的本地 `PopScope` 兜底，不依赖全局处理器顺序。
- **适合顺手的时机**：下一次改动正好碰音乐库多选。
- **判断条件**：改动范围只在这一个组件与它的调用点。
- **边界**：不要顺手重构多选状态模型（`SelectionController` 与回调链已经够用）。
