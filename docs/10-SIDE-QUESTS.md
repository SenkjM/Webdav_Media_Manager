# 10 · 顺手做清单

> 编号 10 · 总索引：[00-INDEX.md](00-INDEX.md)

放大工程里那些**独立、顺手、不值得单开一轮**的小任务。写的是边界与判断条件，不是待办催办单：**发不发布、拆不拆、何时做，都由用户决定。**

## 用法（agent 必读）

1. **不主动执行**。只有用户在清单里挑了某项、或本轮工作天然覆盖到它，才动手。
2. 判断「适合顺手做」必须**四条同时满足**：边界能与其它改动切开；一屏以内的小改或纯机械批量改；不需要新的设计决定；不阻塞当前主线。任一条不满足就留在清单里。
3. **合并前先问用户**，并说清合并理由（共享同一段代码 / 顺路一起验证 / 同一次编译与测试成本 / 改动量很小）。只列理由，不替用户决定。
4. 完成一项就**从清单删掉**，语义按完整文档的写法写进对应功能块，并删掉 99 里的对应条目。
5. 新发现的小任务写进这里，标注它从哪次工作冒出来（来源）、边界条件、判断条件；还没定型的分析仍写在 [99-IN-PROGRESS.md](99-IN-PROGRESS.md)。

## 清单

### T1 · 主题配色：静态引用转上下文取色  `待发布`

- **来源**：主题配色可行性分析（[99 §2](99-IN-PROGRESS.md)）。
- **目标**：`AppColors` 的静态引用改成上下文取色（实测 329 处 / 26 个文件；`app_theme.dart` 自己 77 处是定义，真正要动的是 **25 个文件约 252 处**，逐文件清单见 [99 §1.2](99-IN-PROGRESS.md)），让 `AppTheme.dark` 从死代码变成可用；默认仍是 `ThemeMode.light`，**亮色下行为不变**。
- **适合顺手的时机**：本轮改动正好涉及显示层，或用户在整理界面样式。
- **判断条件**：机械批量改、不引入新设计、完成后亮色表现完全一致（可对照截图验收）。
- **边界**：`nearBlack` / `onDark` 这类语义在暗色下会**反转**，必须单独判断，不能机械替换。
- **隐藏成本（本轮查证）**：大量引用长在 `const TextStyle` / `const BorderSide(color: AppColors.divider)` 这类 `const` 里，取色是运行时值，这些 `const` 全要拆。所以不是纯替换，是「替换 + 拆 const」，要逐文件做、逐文件跑 analyze。
- **验收**：`flutter analyze` + `flutter test`；亮色截图与改动前一致。

### T2 · 主题配色：模式开关与自定义取色  `待发布`

- **来源**：同上；**依赖 T1 完成**。
- **目标**：三态开关（跟随系统 / 亮 / 暗）持久化到 `SettingsService`；自定义配色。
- **先问用户**：自定义的边界是「只让用户改主色 accent」还是「整套色板」。前者工作量小得多，但 `onAccent` 的对比色要跟着算出来。这条**未定就不能开工**。
- **判断条件**：T1 已落地，且用户已经确认了自定义边界。

### T3 · `_SelectableGroupGrid` 的返回键兜底  `待发布`

- **来源**：音乐库子界面返回键那几轮修复（语义见 [03](03-MUSIC-LIBRARY.md)）。
- **目标**：专辑 / 流派网格的子界面（`_TrackListPage` 之外的那条路径）也补上同样的本地 `PopScope` 兜底，不依赖全局处理器顺序。
- **适合顺手的时机**：下一次改动正好碰音乐库多选。
- **判断条件**：改动范围只在这一个组件与它的调用点。
- **边界**：不要顺手重构多选状态模型（`SelectionController` 与回调链已经够用）。

### T4 · 多语言地基：把 l10n 接线接上  `待发布`

- **来源**：多语言可行性分析（[99 §3](99-IN-PROGRESS.md)）。实测 944 条中文字面量、61 个文件，目前 `flutter_localizations` 未引入、无 `l10n.yaml`、无 `.arb`。
- **目标**：`flutter_localizations` + `l10n.yaml` + `app_zh.arb` / `app_en.arb` + `MaterialApp` 接线；ARB 里**只放一个试点模块**的条目，其余文案一律不动。
- **不适合单独做**：地基本身不改任何用户可见文案，单独合并没有交付价值，必须同一轮里带一个模块。
- **先问用户**：目标语言（中 + 英？）与 key 命名规则。**这两条没定就不能开工**，定错了后面 944 条要返工。
- **判断条件**：用户已定目标语言；同一轮里带一个模块的文案；不动枚举与持久化值。
- **边界**：不碰 [99 §3](99-IN-PROGRESS.md) 里那三类结构性问题（枚举显示名、被持久化的值、后台文案），它们必须在批量替换**之前**单独处理。
- **验收**：`flutter analyze` + `flutter test`；切换语言时只有试点模块变化，别处仍为中文。

### T5 · 平台侧资源改为可翻译  `待发布`

- **来源**：同上。应用桌面名目前来自 gradle 的 `manifestPlaceholders["appName"]`，下载通知渠道名是 `download_notification_service.dart` 里的 `kDownloadChannelName` / `kDownloadDoneChannelName` 常量。
- **目标**：应用名走 Android `values-en/strings.xml`；通知渠道名改为按语言取名，并**启用新的渠道 ID**（已创建的渠道改名不会更新系统里的显示）。
- **适合顺手的时机**：下一次改动正好碰通知或打包配置。
- **判断条件**：`values/strings.xml` 目前**不存在**（已核实），所以这是新增而非改写；渠道 ID 变更会让老用户看到新旧两个渠道，需要接受这一点。
- **边界**：不要顺手改通知的其它行为（[07](07-NOTIFICATIONS.md) 里渠道参数两侧必须一致那条约束仍然有效）。
