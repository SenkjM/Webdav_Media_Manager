# 00 · 文档索引与项目约定

面向人类开发者与 coding agents 的**唯一入口**。文档按「功能块」组织：每篇讲清一块功能对用户的语义、可观察行为，以及它在代码里的实现位置。**不写验收清单，不写过程记录。**

## 1. 文档怎么写、放哪

- 全部文档平铺在 `docs/`，文件名 `NN-NAME-IN-CAPS.md`（两位数字编号 + 大写英文名）。
- `00` 固定是本文件。其余按功能块递增，见下表。
- 新增文档：取下一个可用编号，在下表登记一行。**不要建子目录、不要用字母前缀、不要另立「归档 / 活跃」状态**——文档写的是现状；与代码冲突时以源码与测试为准，然后回来改文档。
- 想写计划，就写进对应功能块的文档里，并显式标注「计划（未实现）」。不要单开计划文档。

## 3. Agent 编码约束

1. **先读本索引，再读对应功能块文档**；改动前确认它描述的就是现状。
2. **分支**：main 只有用户明确允许才可合并；beta 用于一般工作保存；新功能基于 beta 开独立功能分支；dev 是重大破坏性改动的历史线。并线至 main / beta 用标准 PR，不得破坏 beta 与 main 的父子关系。
3. **CI**：不要为了看构建结果给 workflow 加 `on: push`，不要擅自 `gh workflow run`，不要推 beta / main，不要打 Pre-release——除非用户明确要求。细节见 [09](09-MISC.md)。
4. **改完跑** `flutter analyze` 与相关 `flutter test`；改核心逻辑优先跑 [09](09-MISC.md) 列出的测试入口。
5. **密钥一律不打印、不提交**：keystore、`key.properties`、token、`.env`、secrets。
6. 提交信息用简短英文前缀（`feat:` / `fix:` / `docs:` / `deps:` / `ci:`）+ 说明。
7. UI 文案用中文，标识符 / 路径 / API 名保持英文。保持 AGPL-3.0 头。

## 4. 项目整体规划

**定位**：Android-first 的 WebDAV 媒体客户端。音频「先下载到本地缓存再播放」，视频走远端流式播放，两者都不做「边下边播的隐式入队」。当前主线是稳定性与体验细节，不是新功能扩张。

**近期（进行中）**：见 [04](04-DOWNLOAD-QUEUE.md) 的「后台下载 `fail host lookup`」与 [02](02-NETWORK-LIBRARY.md) 的「文件动作模型」两节——都在对应功能块文档里标注为未实现。

**路线图（规划快照，未排期，不要当成已实现能力）**：

- **WebDAV 管理**（高）：在现有网络库上扩展上传、移动 / 复制、属性查看、批量操作、回收站与覆盖冲突策略。已有新建文件夹、重命名、删除。
- **国产 ROM 媒体体验**（高）：ColorOS / 一加等机型的媒体通知与后台保活加固。
- **视频播放体验**（中）：缓冲进度条第二层、空闲自动隐藏控件、手势引导。
- **同步体验**（中）：冲突可视化，云端分片整理与审计体验；格式约束见 [08](08-SYNC-AND-BACKUP.md)。
- **启动与低端机体验**（中）：压启动耗时与资源占用。
- **音乐输出后端**（低）：AudioTrack / AAudio 等可选输出后端；成本较高。
- **无障碍与多语言**（低）：语义标签、字号适配、多语言。
- **跨平台**（低）：iOS / 桌面端仅作远期评估，Android-first 不变。
